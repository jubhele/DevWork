## Goal
Allow portal users to have more than one role simultaneously. The existing system uses a single `role` column on `bf_users` and a `bf_role_permissions` lookup table. The change adds a `bf_user_roles` junction table, updates the PHP auth layer to check all of a user's roles when evaluating permissions, and updates the portal UI to show checkboxes instead of a single select for role assignment.

## Model Recommendation
Task tier: 3-Complex
Recommended model: Opus 4.7  Trust score: 10/10
Active model: Sonnet 4.6  Status: under-powered for this task — acceptable given the well-bounded scope

## Decisions
- Keep `bf_users.role` as the "primary role" (for display and backward compat with mobile bearer path) — populated from the first role in `bf_user_roles` for each user
- Backfill `bf_user_roles` from existing `bf_users.role` in migration (idempotent via `INSERT IGNORE`)
- `can()` in PHP now checks the union of all roles in `bf_user_roles`; explicit `$role` arg still works for single-role checks
- JS `can()` updated to check `SESSION.roles` array (falls back to `[SESSION.role]`)
- `roles` array stored in session at login and included in `/me` response — stale until re-login (same as current behaviour for single role)
- Safety-officer role added to create/edit modal (was missing previously)

## Work Done
- `install/migration_user_roles.sql` — new file; creates bf_user_roles, backfills, adds FK
- `includes/auth.php` — added `_user_roles()` helper; updated `can()` and mobile bearer path
- `api/auth.php` — login and mobile_login now include `roles` in session/response
- `api/users.php` — GET returns roles array per user; POST/PUT accept `roles` array and persist to bf_user_roles
- `portal.js` — `can()` multi-role; create/edit modals use checkboxes; renderUsers shows role pills; tech dropdowns filter by roles array; firstPage and dash-sub handle multi-role
