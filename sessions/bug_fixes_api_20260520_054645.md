## Goal
Fix four critical backend bugs identified by analysis of the PHP API files: a REST-violating mass UPDATE on every GET, missing database transactions on batch payment inserts, a flawed duplicate-statement check that only covered one status, and unsanitised SQL in admin.php (noted but no fix file provided for admin.php this session).

## Decisions
- Removed the auto-overdue UPDATE from invoices.php GET entirely rather than throttling it. A cron job is the correct home for this; no stub was added since the trigger mechanism is external.
- Wrapped the entire payments foreach in START TRANSACTION / COMMIT with a ROLLBACK catch. Moved the empty-$logged guard to after the try/catch so a no-op batch still returns a clear error without leaving an open transaction.
- Changed the statements duplicate check to drop the `AND status = 'pending_approval'` clause so any same-day statement (regardless of current status) blocks re-generation.
- admin.php SQL escaping bug noted; no fix applied this session — file was not provided.

## Resumed 2026-05-20 — Extended Analysis Round

### Additional fixes applied

**dashboard.php**
- Removed the same `UPDATE bf_invoices SET status='Overdue'` mass-update that was duplicated here from invoices.php.

**approvals.php — two bugs**
1. Casing: `$status` (correctly capitalised 'Approved'/'Cancelled') was computed but `$decision` (lowercase 'approved'/'rejected') was bound to the UPDATE and returned in the API response. Fixed both callout and quote blocks to bind `$status`.
2. `client_name` source: `approved_by` was built from `$b['client_name'] ?? 'Portal'`, but the frontend only sends `decision` and `notes`. Fixed by adding `client_name` to both PATCH SELECT queries and reading it from the DB record.
3. As a side-effect, moved `$status` computation above the first table lookup so it is shared between callout and quote branches (no duplication).

**callouts.php — two auto-invoice blocks**
- `confirm_closure` action: wrapped `db_insert(invoice)` + `db_exec(callout UPDATE)` in a transaction. Failure rolls back and returns a JSON error.
- Client-closes auto-invoice block: same transaction wrap. Failure rolls back with `error_log` instead of `json_err` because the parent status-update (callout → Completed) already committed; a failed auto-invoice should not undo the closure. `$inv_ref` is nulled on rollback so the email and audit are skipped cleanly.

**users.php**
- Replaced `(int)(bool)$b[$f]` with `(int)filter_var($b[$f], FILTER_VALIDATE_BOOLEAN)` so the string `"false"` is correctly treated as falsy. Without this, admins could not deactivate users if the JS client serialised the boolean as a string.

## Blockers / Next Steps

## Learnings
- The payments loop was doing three separate unguarded writes per invoice — always wrap multi-step financial writes in a transaction.
- Status-scoped duplicate checks are a common source of phantom duplicates when records progress through a workflow; always check on the natural key (date/entity) not on a transient status field.
- Model selection was correct for this tier; no trust score update needed.
