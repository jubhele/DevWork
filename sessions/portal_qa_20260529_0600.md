## PHP Safety  [ISSUES FOUND]

**FLAG — auth.php:208 — `ON DUPLICATE KEY SET` (invalid SQL syntax)**
The mobile rate-limiting INSERT in `api/auth.php` uses the wrong clause:

```php
// api/auth.php line 207–213
db_exec(
    "INSERT INTO bf_mobile_rate_limits (ip_address, device_id, fail_count, locked_until)
     VALUES (?, ?, 1, NULL)
     ON DUPLICATE KEY SET          ← WRONG — MySQL syntax is ON DUPLICATE KEY UPDATE
       fail_count   = fail_count + 1,
       locked_until = IF(fail_count + 1 >= 5, DATE_ADD(NOW(), INTERVAL 15 MINUTE), NULL)",
    [$ip, $device_id]
);
```

MySQL will throw a parse error on `ON DUPLICATE KEY SET`, meaning the entire
`mobile_login` fail-path will throw an exception. The rate-limit counter is **never
incremented** and mobile brute-force protection is silently non-functional.
Mobile login accepts unlimited password attempts with no lockout.

All other PHP checks passed:
- No raw `$_GET`/`$_POST` in SQL — all queries use prepared statements via `db_row`/`db_exec`/`db_select`.
- No `echo $_GET`, `echo $_POST`, or `eval()` found in any reviewed file.
- No hardcoded credentials in portal-facing code. `bhekani_bo.php` (contains `BHK_KEY`) is in `dev-only/`, which is blocked by `.htaccess` and `router.php` deny rules — not accessible from the web.
- RBAC guards: all API endpoints call `require_auth()`. Sensitive endpoints call `require_perm()`. Verified in `api/safety.php`, `api/files.php`, `api/auth.php`.
- `get_pagination()` casts `$limit`/`$offset` to `int` before interpolation — safe.
