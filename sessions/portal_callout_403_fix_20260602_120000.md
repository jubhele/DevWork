# Session: Portal — Callout PUT 403 Fix
Date: 2026-06-02
Provider: Claude Code

## Goal
Admin user getting 403 "Permission denied" when trying to update a callout status via the Update Status modal. Two PUT requests to `/api/callouts.php?id=CO-2024-0001` both return 403.

## Model Recommendation
Task tier: 1-Fast
Recommended model: Haiku 4.5  Trust score: 9/10
Active model: Sonnet 4.6  Status: over-powered

## Root Cause
`callouts.php:208` calls `require_perm('callout.update')` as a broad gate before the granular field checks. The permission `callout.update` was **never inserted into `bf_role_permissions`** in any migration — it is missing from `rbac_full_migration.sql` and `combined_migration.sql`. Because only `sysadmin` role bypasses the permission check, every non-sysadmin user (including admin) gets a 403 at line 208.

## Decisions
- Add `callout.update` to: sysadmin, admin, manager, admin_clerk, call_logger, junior_tech, senior_tech
- client_support, viewer, client do NOT get `callout.update` (they can view but not edit)
- Fix delivered as a patch migration `fix_callout_update_permission.sql` + update `rbac_full_migration.sql` for fresh installs
- The existing granular checks at lines 220-221 (`callout.update_status`, `callout.assign_po`) remain unchanged — they correctly narrow permissions within the update path

## Work Done
- Created `install/fix_callout_update_permission.sql` — patch to run on live server
- Updated `install/rbac_full_migration.sql` — added `callout.update` rows and comment row in matrix

## Blockers / Next Steps
- Run `fix_callout_update_permission.sql` on the live MySQL server to apply the fix
- Verify in portal: admin can open Update Status modal and save without 403

## Learnings
- `callout.update` permission existed in PHP code but was never seeded to the DB — a naming gap between the code and the migration
- When adding a new granular permission to PHP, always grep the migration SQL to confirm it is seeded before deploying
