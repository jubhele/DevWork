## Issues Found

### A — Toast Type Inconsistencies
- `toast('Loading data…', 'ok')` — green success toast for a loading state. Wrong semantic.
- `toast('${id} rejected')` — no type; rejection should be neutral/info.
- `toast('${id} deleted')` — no type (×3 locations).
- `toast('Status updated…')` — no type.
- `toast('PO assigned…')` — no type.
- No `.toast.info` or `.toast.warn` CSS classes defined.

### B — Post-Action Flows (no "what next" guidance)
- After saving a callout → lands on Call Log with just ref toast. No hint to assign technician/PO.
- After saving a quote → lands on Quote Log with just ref toast. No hint about approval queue.
- After saving an invoice → lands on Invoice list with just ref toast. No hint to click Send.
- After logging a payment → stays on same page with no redirect. Dead end UX.

### C — Delete Confirmation Dialogs
- All three delete paths (callout, quote, invoice) use bare `confirm('Delete ${id}?')`.
- No "cannot be undone" warning. One mis-click loses a record permanently.

### D — Required Field Indicators Missing
- Log Call form: Client and Service fields are required but have no `*` marker.
- New Quote form: Client field required, no `*`.
- New Invoice form: Client, Amount, Due Date required — no `*` on any.
- Validation only happens on submit via error toast, leaving users confused about which field failed.

### E — PAGE_INFO Content Issues
- `p-new-callout` FAQ: "Assigned users receive a notification" — **inaccurate**. No notification system exists.
- `p-contact` (portal enquiry page) has no PAGE_INFO entry — ? button shows blank guide.
- `submitEnquiry` action (portal contact form) does nothing but show a toast — silently drops all form data.

### F — initNewQuote Role Check
- `SESSION?.role === 'senior_tech'` — misses multi-role users where senior_tech is not the primary role.
- Should use `!can('quote.approve')` which correctly checks permission rather than exact role string.

## Decisions
- **D1**: Post-action toasts extended with actionable next-step text (not a separate banner).
- **D2**: Log Payment redirects to p-invoices on success — natural next action is to verify the invoice is marked paid.
- **D3**: Delete confirmation updated via template literal multiline string (browser confirm still used — modal upgrade is a future task).
- **D4**: Required `*` markers added in portal.php HTML; `.req` class already styled red.
- **D5**: PAGE_INFO FAQ corrected to say "the callout appears in the Call Log — no automatic notification is sent."
- **D6**: `can('quote.approve')` used in `initNewQuote` for accurate role detection.
- **D7**: Added `.toast.info` (blue) and `.toast.warn` (orange) to portal.css.

## Blockers / Next Steps
- The portal contact enquiry form (`submitEnquiry`) still shows a fake success toast with no actual API submission — flagged but not fixed in this session (would require a new server endpoint or email integration)
- Safety file deactivate button uses a trash-can icon which implies deletion — a UX improvement for a future session
- Delete confirmations still use browser `confirm()` — a custom modal would be more on-brand; deferred

## Learnings
- The `initNewQuote` role check was based on `SESSION.role` (single primary role string) instead of the permission system. All role-based UI logic should use `can()` which checks all assigned roles, not just the primary one.
- Post-action toast messages are the primary user orientation signal — always include what the user should do NEXT, not just what just happened.
- The portal contact enquiry form in p-contact was entirely non-functional (no API call). Always verify that form submit handlers have a real payload, not just a toast.
- `.toast.info` and `.toast.warn` CSS classes were missing despite the code using those type strings — the toast would just show the default styling. Always check CSS when adding new type variants.
