## Learnings (addendum)
- `.gitignore` does not hide a path already tracked in the index — including gitlinks (mode 160000) left over from a removed/never-configured submodule. `git rm --cached` is required regardless of ignore rules. When auditing for "project X still tracked in root repo," check both `git ls-files | grep` (full tree) and `git ls-files -s | grep 160000` (gitlinks) — they're different failure modes needing the same fix.
- `git commit -- <pathspec>` on a path that's simultaneously covered by a *new* `.gitignore` rule can silently drop that path from the commit even though it was staged. Verify with `git ls-files -s <path>` (or `git show --stat`) after any commit involving a just-ignored path, rather than trusting the commit output alone.

## Learnings (addendum 3)
- Per-project `.gitignore` files need periodic audit against constitution §7a/§7b conventions (`_backups/`, `temp/`, `dev-only/`-style scratch dirs) — a rule scoped to one subdirectory (`BlackFire Portal/**/_backups/`) does not catch the same folder name recurring at a different path (repo-root `_backups/`). When adding an ignore rule for one instance of a pattern, check for sibling instances at other path depths in the same repo.
- Bundling an untracking fix into the same `git add`/commit cycle as unrelated pending feature work (rather than `git add <specific-path>`) produces a correct but poorly-scoped commit. When the goal is a clean, isolated hygiene commit, stage explicitly by path rather than relying on whatever the working tree already has staged.
