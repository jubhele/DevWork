## Learnings
- Sysadmin "always sees everything" instructions from the user can conflict with existing deliberate least-privilege designs in the code (here: an audited break-glass override). When that happens, surface the conflict and the existing design's rationale before changing it, rather than assuming the instruction implies the design was a bug — confirmed this via AskUserQuestion before touching code.
- constitution-hook.ps1's `ProjectBind` event needs a stable session ID/transcript path that wasn't available in this environment; when that happens the session log falls back to the `_workspace` bootstrap log even though the work is clearly project-scoped — worth investigating the hook/provider adapter so BlackFire work doesn't end up logged outside `BlackFire\sessions\`.
- A scope/permissions change is not "done" after editing the shared `scope_policy.php` helper — every endpoint that hand-rolls its own company/scope predicate (like the old `api/audit.php`) needs to be re-audited individually, since they don't all automatically inherit fixes made to the shared context builder. Should grep for `allowed_company_ids(` and `company_profile_id IN` across `api/` before considering a scope-model change complete.
- Code review + `php -l` is not "testing" per this workspace's QA standard — must be followed by live click-through verification before a fix is reported as confirmed working. **Confirmed twice by this session**: (1) live testing caught a real SQL syntax bug (empty `WHERE` clause) that code review and lint had both missed; (2) a live browser screenshot caught the 200-row-window filter bug that curl-only API testing had missed, because the bug was entirely in frontend JS behavior invisible to backend testing.
- This workspace's existing `qa_tracker_session.php` (localhost + token gated) is the correct, already-established pattern for standing up an authenticated test session against real data without needing real credentials — reuse it instead of writing a new one. Do not create new sessions impersonating a specific named real user's identity for testing (harness auto-mode classifier correctly blocks this); use existing generic/role-based test accounts instead, or stop and ask.
